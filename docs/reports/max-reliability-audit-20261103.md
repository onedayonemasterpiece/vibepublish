## 0. Правила, которые уже действуют для TG/VK и обязательны для MAX

Источник: [аудит 27.10, §18–18.1](https://github.com/onedayonemasterpiece/vibepublish/blob/audit/publish-reliability-20261027/docs/reports/publish-reliability-audit-20261027.md), skill `docs/llm/vibepublish-social-skill.md`, `AGENTS.md` (devserver-simplicity).

1. **Конечный исход без человека.** Каждая доставка заканчивается: ссылка/queue_ref **или** понятный отказ с кодом. Состояний «needs_review / ручная проверка» нет.
2. **Доверяем сети.** Если MAX показал опубликованный/запланированный элемент с нашим текстом — это успех. Повторных проверок по хешам картинок, скачивания опубликованных фото, сверки скриншотов — нет.
3. **Сети независимы.** Сбой MAX не задерживает TG/VK.
4. **Временные сбои повторяются** внутри фиксированного горизонта (сейчас +15 мин / время отложки − lead), постоянные — сразу понятный отказ.
5. **Без космолётов.** Нет нового состояния/флага/повтора без наблюдаемого сбоя. Ожидаемый результат — **чистое удаление кода**, а не прирост.

## 2. Найденные дефекты (по убыванию вреда)

### M1. Любой сбой предварительной проверки = окончательный отказ без повторов
`adapters/max/bridge.py` `inspect()` превращает **все** `DomainError/MaxBlocked` (в т.ч. `OpenBlocked` с `category=timeout|ui_assertion_failed|unavailable_ui`, `profile_busy`, `browser_owner_busy`) в `Capability('needs_review')`; `prepare()` поднимает `max_preflight_needs_review`, которого **нет** в `worker.TRANSIENT_ERRORS`. Итог: медленная загрузка web.max.ru → публикация в MAX сразу провалена.
**Нужно:** разделить: временные (таймаут/UI не загрузился/профиль или браузер заняты/навигация) → отдельный код из `TRANSIENT_ERRORS` (например `max_ui_unavailable`, `max_profile_busy`) → штатный повтор 5/15/30/60 c в горизонте; постоянные (`needs_auth_or_wrong_account`, `target_denied`, политика цели, лимиты текста/медиа) → конкретный код, понятный отказ. Слово `needs_review` из MAX-пути публикации убрать.

### M2. Повторная проверка фото после публикации (запрещена владельцем)
`bridge._download_binding` + `live._download_media` скачивают опубликованные фото через UI и сверяют хеши; несовпадение → `OutcomeUnknown('max_terminal_download_mismatch')`. Именно здесь падал Chrome (INC-2026-10-10). MAX перекодирует фото, поэтому хеш и не должен совпадать.
**Нужно:** удалить скачивание/сверку из пути publish/reschedule/edit. Успех = найден native элемент с нашим текстом и нужным числом вложений (`media_check='provider_identity_only'`). `bind_download_media` для MAX — удалить или оставить только для явного чтения архива, если оно кому-то нужно (проверить использование).

### M3. Политики целей запрещают нормальные сценарии
`live.mutation_preflight`: `scheduled_only` → «сейчас» запрещено (`immediate_publication_denied`); `publish_channel` → отложка запрещена (`channel_publish_only`); immediate разрешено только `test_group`.
Владельцу нужен MAX как TG/VK: **и сейчас, и отложенно** в любую привязанную цель, если UI MAX это умеет (в канале есть «Отправить позже», в группе — «Запланировать пост», см. `queue.py:110`).
**Нужно:** проверить вживую, какие режимы UI доступны в каждой цели, и разрешить их. Политику свести к факту «что умеет UI», а не к запретам «на всякий случай».

### M4. Чтение ленты MAX не укладывается в срок
`provider_read_deadline` для `feed` обоих алиасов. Без чтения ленты нет ссылки на опубликованный пост (а readback после «сейчас» нужен для ссылки).
**Нужно:** найти, на каком шаге уходит время (лог шагов уже есть — `observed()` фазы), упростить чтение до «последние N строк ленты, найти наш текст». Без «exact_*_verified» сверок.

### M5. `needs_auth` у второй цели
`max_224b98c2579885727f4c` — `needs_auth`. Это либо истёкшая сессия, либо цель привязана к другому аккаунту.
**Нужно:** выяснить причину по коду/логам (не по догадке). Если нужна повторная авторизация по QR — это единственный шаг владельца: сообщить ему один раз в координационный тред, что именно сделать. Остальное время отказ должен быть понятным: `max_needs_auth`, а не общий needs_review.

### M6. Переусложнение
~4 400 строк, ~270 разных кодов `MaxBlocked` (`native_*_unverified`, `*_changed`, `visual_*`, палитры реакций, скриншот-классификатор `visual_recovery`). Каждая лишняя проверка — ещё один способ отказать при живом посте.
**Нужно:** в пути публикации оставить: открыть цель → ввести текст/вложения → (время) → Send/Save → найти свой элемент → ссылка/queue_ref. Сверки «до/после», визуальное восстановление, повторные чтения — удалить, если они не закрывают наблюдаемый сбой. Реакции/ответы/пересылки — вне этого задания (не трогать, но и не держать их проверки в пути publish).

### M7. Диагностика
`production_worker.max_lane` логирует только класс исключения (`MAX provider lane exception: %s`, `type(exc).__name__`). При простое полосы (браузер занят Browser Bridge, профиль не найден) владелец не видит причину.
**Нужно:** логировать код `MaxBlocked`/`DomainError` и фазу (без текста постов/URL/DOM) при старте/падении полосы и на каждом отказе доставки.

### M8. Тесты MAX не запускаются вне прода
В обычном окружении `tests/browser/max/**` падают без браузеров Playwright (на 27–29.10 ~300 «средовых» падений). Регрессии MAX никто не видит.
**Нужно:** в среде исполнителя установить `playwright==1.63` + `chromium-headless-shell` (как в проде), прогонять `tests/browser/max` и `tests/providers`/`tests/runtime` перед PR; новые тесты — на поведение M1–M4, не на внутренние сверки.

## 3. Чего НЕ делать
- Не вводить локальный планировщик/таймер вместо нативной отложки MAX.
- Не добавлять новых «защитных» проверок, режимов и флагов; не повторять Send/Save автоматически после клика (после dispatch — только наблюдение тем же attempt).
- Не трогать Telegram/VK.
- Не публиковать боевые посты для проверки вне согласованного теста (см. приёмку).

## 4. Порядок работ (каждый пункт — отдельный небольшой PR)
1. M7 (лог кода/фазы) — чтобы следующие шаги опирались на факты.
2. M1 (классификация отказов + повторы) + тесты.
3. M2 (удаление скачивания/сверки фото) — ожидается удаление кода.
4. M4 (чтение ленты) и ссылка на опубликованный пост в ответе.
5. M3 (режимы «сейчас»/«отложить» по факту UI) после живой проверки UI.
6. M5 (needs_auth: причина; при необходимости — одно сообщение владельцу).
7. M6 — чистка непокрытых наблюдаемыми сбоями проверок в пути publish.

Каждый PR: net lines, что сознательно не добавлено, таблица самопроверки (`AGENTS.md`), тесты, выкладка только из `origin/main` с проверкой предка (`git merge-base --is-ancestor <running> <candidate>`, running читать из cmdline процесса).

## 5. Приёмка (живая, не CI)
В `max_lovekenig_announcements` (и во второй цели после M5) через обычный MCP:
1. Пост «сейчас» с текстом → `verified` + ссылка.
2. Пост «сейчас» с фото → `verified` + ссылка, без скачивания фото.
3. Отложенный на +3 дня пост с фото → `provider_scheduled` + queue_ref.
4. Тот же пост вместе с TG и VK → все три сети независимо доходят.
5. Искусственно медленный/недоступный UI (offline-тест) → повтор и затем либо успех, либо понятный отказ с кодом; ни одного `needs_review`.
Тестовые посты удалить сразу после проверки (или явно передать владельцу список на удаление).

Отчёт по каждому шагу — в координационный тред: PR, коммит на проде, operation_id и ссылки.
