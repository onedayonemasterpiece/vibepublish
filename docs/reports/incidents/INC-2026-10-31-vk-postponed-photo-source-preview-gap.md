# INC-2026-10-31 — отложенный VK-фотопост: нет доступного изображения для колоризации

Status: `Open`  
Сквозной сценарий: `Not done`.  
Срез: **31 октября 2026, 12:25 UTC**. Время ниже — UTC, если не указано иное.  
Назначение: фактическая постановка для кодового агента владельца. **Только диагностика; этот документ не изменяет код, runtime, публикации или расписание.**

## Summary

Найден нужный ближайший отложенный исторический фотопост. Авторизованные чтения возвращают текст, время и идентификатор поста, но не дают изображение для передачи в imagegen.

Это **не старый блокер схемы редактирования карусели**. PR #115 уже добавил сохранение исходного native-вложения через `existing.position`. Сохранить фото при `wall.edit` и получить его пиксели для колоризации — разные возможности. Первая описана текущим контрактом; вторую в проверенных инструментах для данного postponed item получить не удалось.

**Побочных эффектов нет:** imagegen не запускался, mutation поста не отправлялась, неопределённого исхода VK-записи нет. Пост должен оставаться отложенным с прежним временем.

Владелец прямо исключил браузер. Решение должно работать через штатные авторизованные инструменты/API. Блокировка открытия браузера относится к разрешениям ассистента и не является ошибкой VibePublish.

Репозиторий публичный. Не включены Slack-ссылки, приватные сообщения, email, токены, access_key, подписанные URL и локальные пути. Полный текст ещё не опубликованного поста намеренно не воспроизводится; для точного выбора достаточно scoped item_ref и receipt.

## Impact / целевой сценарий

Направление: основной VK «Полюбить Калининград» (`lovekenig_vk`), не канал анонсов.

Пост: **«Карусели в парке имени М. Калинина. Калининград, 1955–1960»**, источник — архив Евгения Викторовича Ахматова.

Сохранить плановое время: **1 ноября 2026, 19:00 UTC / 21:00 Калининград**.

Ожидаемый результат исходной пользовательской задачи:

1. Получить настоящее фото этого точного отложенного поста без браузера.
2. Выполнить колоризацию от исходного изображения, не синтезировать новое по одному тексту.
3. Первое фото — колоризованное с компактными строками «Автоколоризация», «Полюбить Калининград», источником и CTA «Оригинал →».
4. Второе фото — прежнее native-оригинальное вложение.
5. Сохранить остальной текст; добавить **ровно один** абзац: «Если вы заметили неточность в колоризации, пожалуйста, напишите в комментариях».
6. Тот же postponed post, то же расписание. Без publish-now, отмены/пересоздания, дубликата и изменения Telegram.

Текущая задача — передать диагностику. Выполнение пунктов 1–6 в ходе составления отчёта не производится.

## Воспроизведение: безопасный read-only маршрут

Повторять только под существующим авторизованным владельцем/направлением. Точный внешний envelope сверить с актуальной schema инструмента, не подменять opaque refs между сервисами.

1. `vibepublish_read`: native queue направления `lovekenig_vk`; выбрать указанный postponed item по текстовому ориентиру и `2026-11-01T19:00:00Z`. Сверить queue receipt выше.
2. `vibepublish_read`: query `kind=item` с queue `item_ref=item_0e2458f5ee994568af0dfeec2c146749`; получить свежий exact item. Это read, не edit.
3. Проверить поля exact результата: text/time/provider identity, ordered attachments, наличие поддерживаемого source/preview reference. **Наличие native attachment identity само по себе не означает доступность pixels.**
4. `vibepublish_read`: history по выбранному направлению/посту; наблюдаемое ограничение приведено выше. Tracked publication не является image asset.
5. `vibepublish_media_store`: read-only поиск по двум указанным фрагментам дал 0 результатов. Это не доказывает отсутствие фото во всех provider/storage системах; только отсутствие результата этих запросов.
6. Проверить контракт `vibepublish_asset_preview`: он принимает `resource_uri` вида `vibepublish://assets/{asset_id}`. Queue item_ref и publication ID не являются таким URI. Для этого источника пригодный asset_id не получен.
7. EventsBot имеет собственные opaque item/asset references. В проверенной capability surface не найден scheduled/list_scheduled маршрут; `get_item`/`asset_stage` требуют его собственные refs. **Нельзя передавать Vibe item_ref как EventsBot ref, угадывать scheduled permalink или выдумывать download URL.**

Последовательность фиксирует недостаток доступной поверхности, а не утверждает, что VK вообще не способен вернуть изображение.

## Связь с PR #115 и прежним инцидентом

[PR #115 — VK native in-place carousel edits and transient media retention](https://github.com/onedayonemasterpiece/vibepublish/pull/115):

- Merge commit: `d3d53a8d9176a06fc8c4fa3b8ebf09f544703835`.
- Финальный head: `ef46926090a9f4140fe798a7e7944df4a7cb5443`.

Текущий [VK photo identity binding](../../features/social-operations/vk-media-binding.md) содержит раздел **VK in-place colourization and retention (2026-10-31)**. Он разрешает для свежего exact `item_ref` published **или postponed** поста список:

```json
[
  {"source": {"kind": "asset", "id": "<new_colour_asset>"}},
  {"source": {"kind": "existing", "position": 0}}
]
```

`position=0` адресует native `provider_media` точного исходного поста. Перед edit выполняется CAS; native original не нужно скачивать, повторно загружать или подтверждать CDN-хешем.

**Но для создания new_colour_asset нужно входное изображение.** Native reuse решает сохранение оригинала при публикации, не его передачу генератору.

Предыдущий [утренний диагностический отчёт](INC-2026-10-31-vk-carousel-and-premium-rollout-diagnostics.md) относится к опубликованному акведуку и состоянию до PR #115. Его старые ограничения схемы нельзя считать текущими. Новый кейс — отсутствие доступного source preview/materialization для **отложенного** фото. Этот отчёт не переоткрывает исправленный edit schema gap.

Merge и документация сами по себе не доказывают активный runtime SHA или live acceptance: в рамках этого docs-only отчёта процессы не проверялись. Это нужно отличать от уже наблюдённой tool surface и получить как отдельное доказательство, если расследование требует.

## Root Cause: что доказано, что ещё проверить

**Доказанный операционный пробел:** доступные владельцу чтения идентифицируют точный postponed пост, но не возвращают пригодное для изображения source reference/preview. Штатная `asset_preview` ожидает уже существующий Vibe asset, который этим чтением не предоставлен.

**Не доказано:**

- отсутствие исходных фото в ответе VK transport;
- отсутствие пригодной исходной ссылки в persisted binding;
- ошибка конкретного token scope;
- удаление нужного asset конкретной retention-политикой;
- отсутствие поддержки всех postponed media edit;
- необходимость нового хранилища, сервиса или дополнительной browser-сессии.

Нулевой media-store поиск и `media_projection_not_enabled` не доказывают эти гипотезы.

### Минимальные вопросы кодовому агенту

1. Проследить exact queue/item read: provider response → adapter snapshot → service projection → MCP response. На каком существующем слое доступное фото не передаётся клиенту?
2. Есть ли уже authorised preview/download/materialize путь для provider attachment, который не экспонирован в этом сценарии? Сначала переиспользовать его.
3. Может ли точный `item_ref + position` разрешаться в короткоживущий authorized preview/source через существующий asset/preview механизм? Без требования сохранить original навечно.
4. Отделить два потока: **получение pixels для imagegen** и **native original reuse для wall.edit**. Не заставлять второй зависеть от downloaded bytes.
5. Проверить активную версию сервиса отдельно от merge SHA, если schema/contract и runtime расходятся.
6. Если первичный asset действительно истёк, показать точный источник `asset_expired` и provider recovery путь; не называть любой отсутствующий preview integrity corruption.
7. Нужна ли новая возможность или достаточно перестать отбрасывать существующее поле/маршрутизировать уже поддержанный запрос? Документировать минимальный diff после доказательства.

Ориентиры кода: `contracts/social_mcp_v1.py`, `social_operations/service.py`, `social_operations/assets.py`, VK adapter/transport и обработчик `vibepublish_asset_preview`. Пути проверить по актуальному дереву; новые модули заранее не предписываются.

## Regression Checks / критерии приёмки

### Получение изображения

- По свежему exact postponed item в разрешённом направлении получить реальное исходное фото или пригодный для генерации provider-backed preview **без браузера**.
- Связь с тем же item и attachment position проверяема; нельзя подменить соседним постом.
- Клиент может действительно передать полученное изображение в imagegen, а не только увидеть JSON с названием/ID.
- Чётко указать resolution/preview vs original; не выдавать уменьшенную версию за полный original.
- Чужой target, чужой principal, stale reference и неподдерживаемое вложение корректно отклоняются до побочного эффекта.
- Внешние credentials/access_key и подписанные приватные URL не попадают в публичные логи/документы.

### Полный пользовательский сценарий после отдельного исправления

- Imagegen использует это фото, а не описание сцены.
- Ровно две картинки: колоризация+CTA первой, существующий native original второй.
- Прежний caption сохранён, абзац о неточностях добавлен ровно один раз.
- Тот же native postponed post и время **2026-11-01 19:00 UTC**.
- Не создавать новый post, не публиковать немедленно, не изменять Telegram.
- Перед записью свежий exact read/CAS; после записи авторизованный native readback текста, порядка вложений и schedule.
- При uncertain response сначала reconcile исходный operation/request_key, без второго publish или нового ключа.
- Тесты/merge/asset preview не заменяют проверку конечного provider результата.

## Ограничения и stopping condition

- Браузер запрещён владельцем; никаких cookie/session/DOM обходов.
- Не ослаблять owner scope, CAS, native attachment binding или авторизацию.
- Не вводить бессрочное хранение оригиналов, новые очереди/сервисы/скачиватели без доказанной необходимости. Учитывать уже действующую retention-политику.
- Не требовать CDN fingerprint оригинала для native reuse: это противоречит текущему canonical contract.
- Не изменять код, runtime или пост только потому, что подготовлен этот документ.
- Достаточный итог расследования: точная причина на существующем пути, минимальное исправление при необходимости, тесты и отдельно согласованная сквозная приёмка. При отсутствии полномочий/доступа — точный blocker, а не обход.

**На момент отчёта:** исходная публикация и время неизменны; imagegen не запускался; VK mutation не отправлялась. Документ — новый самостоятельный handoff для владельца и его кодового агента.
