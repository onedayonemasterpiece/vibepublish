# Codex: довести VibePublish MAX до рабочего продуктового результата

**Дата:** 2026-09-08  
**Статус:** Fixed requirements / Implementation Not done  
**Репозиторий:** `onedayonemasterpiece/vibepublish`  
**Основные существующие PR:** [#1 core](https://github.com/onedayonemasterpiece/vibepublish/pull/1), [#2 MAX](https://github.com/onedayonemasterpiece/vibepublish/pull/2)

## 0. Действующая инструкция владельца

Это **новая активная задача для Codex** и источник приоритета для завершения MAX.

Предыдущие отчёты о safety/source-write отказах в отдельных окнах ChatGPT являются историей конкретных попыток доставки конкретного payload. Они **не являются запретом Codex самостоятельно разработать недостающий код** на основании доступного репозитория и фактического поведения MAX.

Codex разрешено самостоятельно читать текущий код, проектировать и писать недостающие изменения как в MAX-адаптере, так и в общем core, worker, storage/application и provider port, когда это необходимо для продуктового результата.

Это **не** инструкция копировать, реконструировать, проксировать или протаскивать ранее отклонённый конкретный payload. Независимая реализация той же продуктовой возможности — нормальная разработка и требуется этой задачей.

Если какая-либо операция записи будет **сейчас** отклонена самой платформой Codex, фиксируй точный текущий отказ и продолжай всё остальное, что от него не зависит. Не наследуй старый отказ как априорный blocker и не останавливай работу только потому, что он описан в истории PR.

Дополнительных согласований владельца на разработку core/MAX и на любые тестовые социальные действия в **«Тестовой группе» MAX** не требуется.

## 1. Продуктовый результат

Нужен не bridge, не fixture и не набор зелёных тестов сам по себе. Нужен **VibePublish с MAX как рабочим полноценным provider adapter**.

Через штатную цепочку:

`MCP → application/core → worker → ProviderAdapter → RealMaxDriver → настоящий MAX Web`

должны реально выполняться и проверяться поддерживаемые MAX операции:

1. публикация обычного текста;
2. публикация текста со ссылками/поддерживаемым форматированием;
3. публикация одного изображения;
4. публикация нескольких изображений/альбома, если это поддерживает используемая поверхность MAX;
5. публикация поддерживаемого видео;
6. чтение опубликованного объекта с точной привязкой к native item/reference;
7. редактирование текста опубликованного объекта без потери его медиа;
8. нативная отложенная публикация средствами MAX, без локального scheduler публикаций;
9. чтение/проверка отложенного объекта и его native времени;
10. перенос времени отложенной публикации **с сохранением медиа и содержимого**;
11. отмена собственной отложенной публикации;
12. удаление собственного опубликованного объекта;
13. reply/reaction/forwarding и другие уже предусмотренные контрактом социальные операции там, где фактический MAX Web их поддерживает;
14. восстановление после browser/worker/process/network failure **без дублирующего внешнего эффекта**.

Если конкретная функция фактически отсутствует в MAX Web для данного типа target/object, это должно быть доказано live-наблюдением и возвращаться как точная capability/unsupported причина. Это не должно блокировать остальные функции.

## 2. Критерий готовности

Задача не закрывается отчётом «частично», «bridge готов», «fixture зелёный», «core recovery отдельно ждёт» или очередным handoff.

Минимальная продуктовая приёмка:

- реальные операции идут **через MCP и worker**, а не обходным CLI;
- реальные mutation/readback сценарии проходят в разрешённой «Тестовой группе»;
- результат каждого effect проверяется через MAX и связывается с исходной operation/attempt;
- edit сохраняет media identity/content;
- reschedule сохраняет media/content и меняет именно native schedule time;
- cancel/delete работают по точному собственному native объекту;
- crash/restart после внешнего effect не создаёт второй пост/правку/удаление;
- native scheduled post способен выйти средствами MAX при остановленном VibePublish;
- обнаруженные особенности реального DOM/UI воспроизведены автоматическими regression tests;
- MAX-код и необходимые core-изменения находятся в GitHub в существующих PR/ветках, CI запущен на точных SHA;
- финальный отчёт перечисляет фактически пройденные live кейсы и ссылки на commits/CI, а не заменяет ими live-приёмку.

## 3. `outcome_unknown` и recovery

Не превращай внутренний статус неопределённости в тупик продукта.

`outcome_unknown` или эквивалентный transient state может быть полезен **в момент**, когда внешний effect мог произойти, а receipt потерян. Нельзя просто повторять effect и нельзя обязательно удалять enum глобально, если он нужен другим providers.

Но для поддерживаемой MAX операции этот статус не должен оставаться terminal dead-end после того, как состояние MAX можно проверить.

Требуемый путь:

1. durable intent/checkpoint до effect;
2. ровно один внешний effect;
3. обычный DOM/native readback;
4. при технически неоднозначном UI — ограниченная визуальная проверка уже существующим Gemini Lite path через общий `GoogleAIClient`/лимитер;
5. свежий native readback после вспомогательного наблюдения;
6. durable evidence binding к исходным operation/attempt/plan;
7. штатный перевод операции в доказанный конечный результат либо точный compensation outcome;
8. штатное освобождение quarantine/fuse после успешного resolution;
9. при restart тот же recovery выполняется без повторного Send/Save/delete.

Существующий исходный тестовый пост, ранее зависший с `outcome_unknown`, используй как первый реальный recovery case: заново проверь объект, заверши исходную operation штатным кодом и очисти тестовый объект штатной MAX-операцией. Не лечи проблему ручным SQL или ручным удалением fuse.

## 4. Границы веток и ownership

Продолжай существующую работу, не создавай третью архитектуру или второй MAX driver.

- **PR #2 / `work/vibepublish-max-web-20260904`**: MAX-specific Playwright driver, selectors, profile/session binding, MAX bridge/wiring, MAX regression/live tests, runbook.
- **PR #1 / `work/vibepublish-core-20260904`**: общие core/worker/storage/application/provider-port изменения, если они действительно нужны для terminal recovery, lifecycle или общего контракта.

Codex может работать в обоих существующих worktree/branches в рамках одной продуктовой задачи. Старое правило «MAX-исполнитель не меняет core» **отменено владельцем**.

Не копируй core внутрь второго имитационного порта MAX. Изменяй настоящий общий core там, где это архитектурно требуется, и затем проверяй MAX на совместимой интеграционной сборке.

Telegram/VK не переписывай без необходимости. Если additive core change затрагивает общий контракт, сохрани обратную совместимость и прогон соответствующих контрактных/core тестов.

## 5. Разрешения для live MAX

### «Тестовая группа»

Разрешены **все необходимые тестовые действия без дополнительного согласования и без лимита количества тестовых объектов**:

- publish/read/edit/delete;
- media;
- native schedule/read/reschedule/cancel и фактический native output;
- reply/reaction/forwarding при наличии поверхности;
- crash/restart/reconcile;
- повторные циклы и cleanup собственных тестовых объектов.

Группа тестовая; используй её для достижения результата, а не останавливайся из-за уже оставленного тестового объекта.

Не меняй участников, права, название группы, авторизацию или чужие сообщения.

### «Ух ты, Калининград!» и «Полюбить Калининград Анонсы»

Сохраняются более узкие разрешения: read-only для существующего контента/очереди и собственные безопасные тестовые **отложенные** объекты с точной последующей отменой. Не делай немедленную тестовую публикацию в реальную ленту без нового явного разрешения владельца.

Недоступность/неоднозначность одного реального канала не останавливает Test Group и остальные работы.

## 6. Авторизация и браузер

Используй уже существующую авторизованную MAX session/profile на DevCoveer. Не трать задачу на новый QR/login, пока текущая сессия валидна.

Не делай logout, не очищай cookies/storage-state и не запускай два конкурирующих Chromium на одном профиле. Если авторизация реально истекла, зафиксируй `needs_auth` как конкретный внешний prerequisite, но продолжай код/replay/остальные доступные проверки.

Production selectors должны происходить из реально обследованного MAX Web. Не выдумывай `data-testid` или synthetic DOM identity.

## 7. Vision fallback

Vision — вспомогательное наблюдение, не отдельная цель и не повод останавливаться после того, как Gemini успешно прочитал скриншот.

При неоднозначном UI:

- сначала обычные DOM/native методы;
- затем при необходимости screenshot **только нужного task-owned объекта/области**;
- Gemini Lite использовать только через существующий `google_ai.GoogleAIClient` и общий limiter;
- локально ранее разрешён конфигурационный файл `/home/dev/projects/my-data-hub/.env`; не копируй его или секреты в Git;
- модель может подтвердить видимый текст/состояние, но конечная operation всё равно завершается кодом core на основании native/evidence binding;
- после vision выполняй свежую нативную проверку.

## 8. Что не считать blocker

Не останавливай задачу из-за следующих исторических формулировок:

- «core recovery однажды не удалось загрузить из окна ChatGPT»;
- «нужен старый recovery ZIP»;
- «MAX исполнитель не имеет права менять core»;
- «нельзя самостоятельно реализовать замену»;
- «исходный `outcome_unknown` запрещает новые тестовые действия в Тестовой группе»;
- «сначала другой агент должен доставить recovery».

Они **не являются действующими ограничениями этой продуктовой задачи**.

Единственный допустимый платформенный blocker — актуальный, воспроизведённый **в текущей Codex-сессии** отказ конкретной необходимой операции, который действительно невозможно обойти нормальной разработкой и который блокирует именно оставшийся продуктовый путь. Даже тогда продолжай все независимые участки задачи.
