### Безопасность отложенных в реальных каналах

Сначала реализуй и проверь точное удаление из очереди и защитные проверки на replay и в тестовой группе, где функция доступна. Различие group/channel UI не игнорировать: перед созданием пробы в реальном канале read-only проверь доступность его команды отмены. Не экспериментируй вслепую с неизвестным destructive menu над редакционным постом.

Каждая проба получает уникальный `run_id/case_id` и нейтральную пометку «VibePublish: технический тест, будет удалён». В реальном канале допускается **не более одной активной пробы одновременно**. Поставь её не ранее чем через 24 часа и внутри реально подтверждённого MAX горизонта; при неподдерживаемом таком запасе ничего не создавай. Перенос также оставляет запас не менее 24 часов. Это выбранный предел безопасного теста, не утверждение о лимитах MAX.

Сразу сохраняй exact remote ID, исходный/новый timestamp с offset, контент/media fingerprint и сведения для точной очистки. После каждого кейса отменяй именно эту пробу и заново проверяй очередь. `finally` cleanup обязателен, но сам по себе не считается доказательством отмены. До окончания текущего прогона не оставляй пробы «на завтра». При неясном результате очистки прекрати новые live-записи в реальных каналах и немедленно сообщи точный объект, срок и риск; не обещай, что локальный флаг предотвратит выход у MAX. Не удаляй чужие объекты и не снимай uncertainty marker ради продолжения.

Нативный выход при выключенном VibePublish и live-инъекции сбоев выполняются только в **Тестовой группе**. Если именно группа не поддерживает нужную поверхность, зафиксируй фактическое ограничение; не используй вместо неё реальный канал для публичного canary. Недоступность одной поверхности не оправдывает отказ от остальных поддерживаемых сценариев.

### Устойчивость к порядку чатов и изменению DOM

Название/поиск используются для первичного разрешения. Дальше хранится проверенная связь `account → native chat identity → alias`; порядок, аватар и подпись не являются identity. Перед заполнением, после awaited callbacks и непосредственно перед воздействием заново сверяй выбранные account/chat/item и режим now/scheduled.

Не использовать `first()/nth()`, координаты, старые ElementHandle, номер строки чата или позицию в результатах поиска для выбора назначения. `nth` допустим только для явно упорядоченных вложений после проверки их контейнера/состава, не для устранения неоднозначности. При совпадении имён — устойчивый ID/deep link из фактического UI; иначе безопасная остановка. Переименование не меняет identity, а пропавшее назначение не заменяется похожим.

Ожидай реальные postconditions, а не фиксированные sleep: готовность списка/поиска, загрузку медиа, открытие нужного меню, сохранение в очереди. После перерисовки reacquire scoped locators. Виртуализированные списки/очереди читаются с явным пределом и пагинацией/признаком неполноты; отсутствие на текущем экране не равно отсутствию поста. Продвижение чата вверх из-за нового сообщения не должно перенаправить действие.

### Функции и доказательство результата

- Положительные сценарии обязательны: text-only now; текст+1 изображение; 2+ изображения в порядке; поддерживаемое видео; native schedule; очередь; edit; in-place reschedule; cancel; delete. Группы и каналы проверяются раздельно. Links/formatting/replies/reactions/native forward — проверить и довести там, где доступно; неподдерживаемое зафиксировать с конкретным UI evidence, не молча урезать исходные данные. MAX forward не подменять копированием. Не расширять задачи на другие сервисы.
- Text-only не должен по конструкции всегда давать unknown. Найди реальную связь своей UI-команды с созданным remote ID/подтверждением и последующим чтением того же объекта. Совпавший текст/время или один новый результат без атрибуции недостаточны. Test marker помогает корреляции, но не должен быть обязательной добавкой к обычным пользовательским постам. Честная неоднозначность по-прежнему остаётся unknown.
- Для cancel/delete не требуй выдуманного MAX tombstone и не объявляй простой пустой экран доказательством. Зафиксируй точный прежний ID, адресное действие/подтверждение и свежий авторитетный readback соответствующего namespace; учти фильтрацию/виртуализацию и переход schedule→published. Документируй реально достижимый уровень доказательства. При недостаточных данных — unknown без повторного воздействия.
- Перенос меняет только native time, сохраняя identity, текст, ссылки, состав/порядок media. Не delete+create. Если MAX действительно меняет identity, докажи нативное соответствие; не угадывай его. Edit текста не должен очищать медиа. Время с offset/IANA context, слишком близкое/прошедшее блокируется, никогда не превращается в now.
- Источник времени исполнения — MAX. После подтверждения очереди операция постановки закончена. Локальные БД/повторы чтения/cleanup deadline — не планировщик будущих отправок. Истечение времени или исчезновение из очереди не доказывают публикацию.
- Используй имеющиеся awaited `emit_progress/checkpoint/before_effect`. Последний guard и durable dispatch marker до эффекта обязательны. Profile lock действует вместе с фактическим владельцем браузера, не только внутри тестового приложения. После возможного клика — observation/reconcile; новый request key не обход неопределённости. Сбой callback/БД до разрешения воздействия означает zero mutation.
- Source SHA и remote media identity различаются: не придумывать SHA перекодированного изображения. В результате — действительный item/queue ref, observed_at, время, проверка текста/медиа, ссылка где существует либо точная навигация, а не фиктивный permalink.

Если нужен replay ответов, используй обезличенные минимальные fixtures; HTTP HAR сам по себе не покрывает WebSocket/ServiceWorker — учти фактический транспорт. Не записывай/не воспроизводи отправки в настоящий MAX из CI и не вызывай MAX endpoints напрямую вместо Web UI.

Не добавляй production-драйверу специальные вымышленные test IDs ради теста. Подмена фреймворка mock-объектом page или копия упрощённого live-кода в tests недопустимы. Replay может моделировать провайдера, но должен иметь независимое от драйвера состояние/счётчик воздействий и проверять exact target, namespace, media, time, causal receipt.

В Git коммитятся **безопасные исходные fixtures и генераторы**, сценарии и их manifest: scenario ID → наблюдавшийся UI state → selector recipe/version → positive/negative test → происхождение и выполненные обезличивающие преобразования. Не копируй всё приложение MAX или весь профиль. Удаляй из captures cookies/auth headers/tokens/storage, реальные телефоны, приватные ID/URLs, чужие тексты и изображения. Сохраняй структуру, нужную для селекторов, с вымышленными данными. Добавь тест sanitization на искусственных secret sentinels. Raw traces/screenshots/HAR/DOM остаются защищёнными локальными artifacts, не публичными GitHub artifacts; на GitHub только отдельно проверенные безопасные результаты.

Live tests запускаются отдельной явной командой с разрешённым session binding и allowlist. Обычный pytest/CI не должен уметь незаметно включить их. В GitHub используй существующий `.github/workflows/ci.yml` и GitHub-hosted runner, без self-hosted runner/профиля/секретов MAX. Установи зафиксированные зависимости и Chromium, запиши версии. Live selector replay и order-drift tests обязательны, отсутствие браузера/fixtures не маскируется skip.

После push выполни чистый checkout точного SHA, прогони сохранённые сценарии, проверь завершение Actions и реальные логи. Любое исправление во время live-отладки должно попасть в коммит и повторный относящийся к нему прогон; не показывай старый зелёный CI для нового кода.

Actual-core integration использует настоящий port/worker/MCP, не surrogate. Если core доступен в GitHub — зафиксируй совместимый core SHA/способ сборки в CI, потребуй `VIBEPUBLISH_MAX_CORE_REQUIRED=1` и ноль пропусков обязательных core cases. Если пока только архив — выполни эти тесты локально, честно оставь **remote core integration blocked**, сохрани независимый MAX live-driver replay в GitHub без core. Не выдавай его за полный сквозной CI и не обходи блокировку доставки ядра. Это ограничение не мешает писать/проверять реальный MAX и его replay.
