# VK wall publication → linked story

Status: `Not confirmed by user`. The owner approved implementation of the server-event approach on 2026-10-11; code/tests do not establish live acceptance.

This is a narrow, explicit exception to the native-only scheduling contract. The wall post remains in VK's native postponed queue. A story is **not** placed in a VK story queue: one approved child is dispatched by the service only after exact readback proves that its own parent wall post is published. There is no general local publication calendar and no automatic stories for other editors' posts.

`publish.linked_story` binds one image asset and link label (a VK `link_text` selector, `VK_STORY_LINK_TEXTS`) to exactly one VK wall target within that publication. The service freezes the image hash and destination grant at admission. Generated or changed images require a new explicit approval. The ordinary story receipt and unknown-outcome protections apply to the child.

The durable dependency, sanitized event receipt, server cursor and child operation are stored in the existing SQLite database. A repeated event, concurrent worker or process restart cannot create a second child. Native event payloads only wake observation; they do not authorize publication and their text/media are never accepted as approved content. The service does exact identity/text/media readback before child creation and exact source readback again in the ordinary story adapter before effect.

VK community Long Poll is a server-to-server API, unrelated to mobile push notifications. Only already configured community event access may be used. No credentials, subscriptions or persistent access are created automatically. Long Poll readiness is reported separately from story capability. If an event is missed or a cursor resets, the worker reads only the explicitly tracked parent identity, at bounded intervals, through 24 hours after its expected publication. It never searches a calendar or creates a replacement wall post. A scheduled VK wall ID is not the final published ID. The service accepts only an explicit provider postponed_id-to-id mapping from the authenticated publication event or a bounded (100-entry) authorized wall feed read, followed by exact published-item text/media readback. Identical content, nearby time and disappearance from the queue never prove that mapping. Missing mapping stays unresolved with linked_story_parent_mapping_unproven; conflicts block. The final Story URL is built only from the verified published ID.

An accepted parent revision change (including edit, reschedule, cancellation or deletion) invalidates a waiting or not-yet-dispatched child. The caller must explicitly approve a new linked-story intent after such a change; a stale event cannot restore the old approval. External changes to parent text/media block the child. Already dispatched stories are not silently deleted or republished. Expired dependencies and uncertain child outcomes require review, never blind retries.

The normal authorized read result optionally includes `native_schedule_origin` with owner_id, postponed_id, published_id and evidence=vk_postponed_id, only when VK explicitly returns a positive native postponed_id on a published item. Absence is unknown; no IDs are inferred from content or time. This supports read-only live verification through the existing injected connection without accessing configuration or credentials.

Live acceptance requires an approved community, time and asset; confirmed event settings; native scheduled wall publication; server event receipt; exact published readback; a visible story with the correct clickable wall link; and duplicate-event/restart observation. Offline tests alone do not mark this feature `Done`.
